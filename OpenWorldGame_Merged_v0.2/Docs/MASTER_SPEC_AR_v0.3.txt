# وثيقة المشروع الرئيسية — لعبة عالم مفتوح واقعية تعمل دون إنترنت

**الإصدار:** 0.3 — مواصفات Android APK + عقد تنفيذ وتحقق صارم لوكيل AI  
**تاريخ المراجعة:** 11 نوفمبر 2026 — أضيف عقد تنفيذ وفحص شامل للملفات والروابط والبناء والاختبارات  
**حالة الوثيقة:** مواصفات وخطة تقنية؛ يوجد نموذج مصدر Unreal أولي باسم MADA | مَدَى، لكنه ليس لعبة مكتملة ولا APK قابلاً للتشغيل.
**المحرك المرجعي:** Unreal Engine 5.8  
**المنصة الأساسية للنسخة الأولى:** Android 64-bit (arm64-v8a) بصيغة APK؛ Windows x64 بيئة تطوير وبناء واختبار مساعدة، وليس منصة التسليم الأساسية  
**نمط اللعب:** لاعب واحد، Offline بالكامل.

---

## 0. بيان الصراحة ونطاق ما أُنجز

هذه الوثيقة تجمع المتطلبات والقرارات التقنية ومصادر التعلم الرسمية وتعليمات وكيل البرمجة. يوجد مستودع GitHub ومشروع مصدر Unreal Engine 5.8 أولي باسم MADA | مَدَى؛ يحتوي حركة شخصية ومركبة rigid-body تجريبية وواجهة UMG وبيئة Greybox تُنشأ وقت التشغيل وحفظاً محلياً. لا توجد أصول فنية نهائية أو خريطة `.umap` أو APK. اجتازت فحوص المضيف الحالية 11 اختبار Python و42 اختبار C++، لكن Unreal Engine لم يُشغّل ولم يحدث بناء أو اختبار لعب/أداء على جهاز؛ لذلك لا توجد نتائج Gameplay أو FPS فعلية يمكن الادعاء بها.

معظم ما يأتي يحدد نطاقاً مستهدفاً وخطة تنفيذ مستندة إلى وثائق ومصادر منشورة؛ التنفيذ الحالي يغطي نموذجاً أولياً محدوداً فقط. أي أصل فني مذكور كمصدر هو مكان يمكن فحصه واختيار أصل منه لاحقاً، وليس أصلاً تم الحصول عليه أو التأكد من رخصة كل ملف فيه.

**الهدف الواقعي:** الوصول إلى لعبة مستقلة بطموح عالم مفتوح وقيادة ومشي ورسوم عالية، تستلهم مستوى الانغماس من ألعاب العالم المفتوح الحديثة، لكن بهوية وأسماء وخرائط وشخصيات وأصول أصلية أو مرخصة. لا يجوز وصفها بأنها بمستوى GTA VI قبل وجود لعبة كاملة واختبارات وأدلة تقارن النتيجة فعلياً.

## 1. الرؤية المختصرة

لعبة عالم مفتوح ثلاثية الأبعاد، فردية، تعمل دون اتصال بالإنترنت، تسمح للاعب بالتنقل سيراً على الأقدام وبالسيارات بين مدينة حديثة ومناطق ريفية وطبيعية متصلة. تركيز التجربة على:

1. حركة شخصية بشرية طبيعية وسريعة الاستجابة.
2. دخول المركبات والخروج منها والانتقال السلس بين المشي والقيادة.
3. فيزياء قيادة قابلة للضبط، مع اختلاف سلوك المركبة حسب السرعة والسطح والطقس.
4. عالم واسع مقسم إلى خلايا تُحمّل عند الحاجة بدلاً من تحميل كل شيء مرة واحدة.
5. حركة مرور وشخصيات غير قابلة للعب لها سلوكيات يومية مبسطة.
6. دورة ليل ونهار وطقس متغير وتأثيراته المرئية والصوتية.
7. حفظ محلي دائم للتقدم والإعدادات والمركبات.
8. واجهة واضحة، مع دعم العربية أولاً وإمكانية إضافة الإنجليزية.

لا تُعد الخريطة الضخمة وحدها لعبة مكتملة. المطلوب أيضاً أنظمة لعب متماسكة، صوت، واجهات، حفظ، أداء، واختبارات.

## 2. قرارات النسخة الأولى

| البند | القرار |
|---|---|
| المحرك | Unreal Engine 5.8 كخط أساس موثق حالياً؛ تثبيت رقم التحديث الدقيق للمحرك عند إنشاء المشروع وعدم تغييره وسط التطوير بلا اختبار ترقية |
| المنصة | Android 64-bit (arm64-v8a) كمنصة تسليم أساسية؛ Windows 10/11 x64 للتطوير والبناء عند الحاجة |
| النمط | Offline / Single Player فقط |
| الإنترنت | لا تسجيل دخول، لا خادم إلزامي، لا تحقق ترخيص أثناء اللعب، لا API خارجي مطلوب لبدء اللعبة |
| الإدخال | شاشة لمس وأزرار افتراضية قابلة للتخصيص؛ دعم يد تحكم وWindows كخيارات إضافية |
| الكاميرا | منظور ثالث للشخصية، وكاميرا قيادة قابلة للتبديل؛ منظور أول اختياري بعد ثبات الأساس |
| اللغة | العربية أولاً، وتصميم الواجهة بحيث يمكن إضافة لغات أخرى |
| التقنية الأساسية | C++ للأنظمة الجوهرية، وBlueprint للربط والتجارب السريعة، وData Assets/Data Tables للقيم القابلة للتعديل |
| النطاق | مدينة + طريق ريفي + طبيعة متصلة، تتوسع لاحقاً بحسب الأداء وتوفر الأصول |

**قرار مهم:** لا نبدأ بخريطة هائلة مكتملة التفاصيل. نثبت أولاً شريحة لعب قابلة للتشغيل (Vertical Slice)، ثم نوسع العالم باستعمال الأنظمة نفسها. هذا ليس تقليلاً من الهدف؛ بل يمنع إنتاج مساحة ضخمة فارغة أو غير قابلة للعب.

## 3. محرك الرسوم والإضاءة

### 3.1 التقنيات المستهدفة

- **Lumen:** إضاءة عامة وانعكاسات ديناميكية للمشاهد الداخلية والخارجية.
- **Nanite:** هندسة عالية التفاصيل للأصول التي يدعمها النظام؛ لا يُفعّل بشكل أعمى على كل Mesh.
- **Virtual Shadow Maps:** ظلال عالية الجودة عند توافقها مع ميزانية الأداء.
- **Hardware Ray Tracing:** خيار جودة للأجهزة المدعومة، وليس شرط تشغيل اللعبة.
- **Temporal Super Resolution (TSR):** رفع الدقة من دقة داخلية أقل عند الحاجة.
- **PBR Materials:** خامات مبنية على Base Color وRoughness وMetallic وNormal وغيرها بحسب نوع السطح.
- **Sky Atmosphere / Volumetric Clouds / Fog:** سماء وضباب وسحب جوية عند الحاجة.
- **Niagara:** مطر ورذاذ وغبار وأوراق متطايرة ومؤثرات بيئية.
- **Post Processing:** Bloom وMotion Blur وExposure وDepth of Field بإعدادات قابلة للإيقاف أو التخفيض.

### 3.2 قواعد واقعية الرسوم

1. لا تجعل كل سطح لامعاً؛ قيمة Roughness يجب أن تتناسب مع المادة.
2. طلاء السيارة يتكون من طبقات مادية مناسبة، مع Clear Coat عند الحاجة، وليس مجرد لون معدني موحد.
3. الزجاج يحتاج إعدادات شفافية وانعكاس واختبارات ليلية ونهارية؛ لا تفترض أن إعداد مادة واحدة يصلح لكل أنواع الزجاج.
4. الانعكاسات في مرايا السيارة عنصر مستقل يحتاج ميزانية GPU واختباراً؛ انعكاس Lumen العام لا يضمن مرآة داخلية مثالية في كل الحالات.
5. المطر لا يعني مجرد Particle Effect: يجب أن يصاحبه صوت، بلل تدريجي للأسطح، اختلاف تماسك الإطارات، آثار ماء، ومسّاحات زجاج إذا توفرت أصولها.
6. Motion Blur وDepth of Field وBloom يجب ألا تحجب الرؤية أو تسبب دواراً؛ اجعلها قابلة للتخصيص.
7. وفّر إعدادات Low / Medium / High / Epic، ولا تفترض أن أعلى إعداد مناسب لكل جهاز.

**قيد تقني:** Lumen وNanite مكلفان حسابياً، وHardware Ray Tracing يحتاج بطاقة ونظاماً متوافقين. وجود هذه التقنيات لا يضمن وحده صورة بجودة لعبة AAA أو معدل إطارات مرتفع.

## 4. حركة الشخصية والتحكم

### 4.1 حالات الحركة

- Idle، Walk، Jog، Sprint.
- Start / Stop / Turn in Place.
- تغيير الاتجاه مع مراعاة سرعة الحركة وزخم الشخصية.
- Jump وLand عند الحاجة لتصميم العالم.
- صعود ونزول الدرج والمنحدرات والعوائق المنخفضة.
- دخول السيارة والخروج منها، مع حركات انتقال مناسبة.
- تفاعل مع أبواب ومقابض وأشياء بيئية مسموح التفاعل معها.

### 4.2 جودة الحركة

- استخدام **Motion Matching / Pose Search** إذا توفرت مجموعة حركات مناسبة ومتوافقة مع هيكل الشخصية.
- استخدام Game Animation Sample الرسمي كمرجع تعليمي أو نقطة أساس قابلة للفحص، لا كضمان أن كل الحركات المطلوبة متوفرة.
- إضافة Foot IK لتثبيت القدمين على الأرض والدرج والمنحدرات.
- معالجة دوران الجذع واتجاه النظر والبدء والتوقف.
- مزج الحركة بحسب السرعة والاتجاه، لا بحسب زر الحركة وحده.
- فصل حركة اللاعب عن منطق الكاميرا وعن نظام التفاعل لتقليل الترابط البرمجي.

### 4.3 حسابات الحركة

- تخزين السرعة بوحدات Unreal القياسية داخلياً، وتحويلها للعرض بوحدة km/h.
- حساب التسارع من تغير السرعة خلال الزمن، مع استخدام Delta Time بطريقة صحيحة.
- مراعاة أن الحركة تختلف بين الأرض المستوية والمنحدر والدرج والأسطح الزلقة.
- لا تستخدم قيماً عشوائية من وكيل الذكاء الاصطناعي على أنها بيانات بشرية حقيقية؛ كل قيمة تضبط عبر Playtests وقياسات.

## 5. المركبات ونظام القيادة

### 5.1 التقنية الأساسية

استخدام **Chaos Vehicles** كبداية لفيزياء السيارات، مع بناء إعدادات منفصلة لكل فئة مركبة. يحتاج كل نموذج مركبة إلى Mesh مناسب، وPhysics Asset/Collision، وعجلات، ومخطط تحكم، ومنحنى عزم محرك وإعدادات تعليق. لا تصبح الفيزياء واقعية بمجرد تفعيل Plugin؛ يجب ضبطها واختبارها.

### 5.2 خصائص القيادة المطلوبة

- دفع أمامي أو خلفي أو رباعي بحسب إعداد المركبة.
- منحنى عزم المحرك، RPM، نسب ناقل الحركة، سرعة قصوى تقريبية داخل اللعبة.
- وزن المركبة ومركز الكتلة.
- تعليق النوابض والمخمّدات، وارتفاع الهيكل.
- نصف قطر الإطار، احتكاك الإطار، الفرملة، والجر.
- اختلاف الإحساس بين سيارة صغيرة وSUV وسيارة رياضية ومركبة ثقيلة.
- واجهة عدادات: السرعة km/h، RPM، الغيار، الوقود إذا قرر التصميم إضافته.
- أصوات محرك تتغير مع RPM والحمل والسرعة، وأصوات إطارات تختلف حسب السطح.

### 5.3 تأثيرات الطريق والطقس

- سطح أسفلت جاف، أسفلت مبلل، تراب، حصى، عشب.
- لكل سطح إعدادات احتكاك وصوت وإظهار آثار الإطارات.
- المطر يخفض التماسك داخل محاكاة اللعبة بدرجات قابلة للضبط؛ لا تستخدم نسبة واحدة ثابتة لكل السيارات والأسطح.
- معالجة انزلاق الإطارات والفرملة والتوجيه بما يتناسب مع سرعة المركبة.
- اهتزاز كاميرا خفيف ومحدود مرتبط بحالة الطريق، مع خيار تقليله.
- تلف بصري محدود للمركبة عند التصادم، مثل الخدوش أو انبعاجات تجميلية إن توفرت نماذجها؛ لا حاجة لمحاكاة إصابات أشخاص أو تفاصيل مؤذية.

### 5.4 انتقال اللاعب بين الشخصية والسيارة

- فحص قرب اللاعب من باب صالح للاستخدام.
- التحقق من أن المقعد متاح وأن السيارة ليست في حالة تمنع التفاعل.
- تشغيل حركة الدخول، ثم نقل التحكم إلى المركبة بعد اكتمال نقطة الانتقال.
- عند الخروج، التحقق من وجود مساحة آمنة وخالية بجانب السيارة قبل وضع الشخصية.
- إعادة ربط التحكم والكاميرا والواجهة بطريقة لا تترك اللاعب عالقاً أو داخل Collision.
- دعم مقاعد متعددة فقط بعد إتمام مقعد السائق.

## 6. العالم المفتوح ودمج المناطق

### 6.1 البنية

استخدام **World Partition** لتقسيم العالم إلى خلايا قابلة للتحميل والتفريغ حسب موقع اللاعب، و**Data Layers** لفصل المناطق أو حالات العالم، و**HLOD** لعرض نسخ بعيدة مبسطة من المباني والأشجار والتضاريس، و**Level Instances** لإعادة استخدام أجزاء معيارية.

### 6.2 تصميم المناطق

- منطقة حضرية: شوارع، تقاطعات، أحياء، مبانٍ، مواقف، محلات بواجهات خارجية.
- منطقة ريفية: قرى صغيرة، طرق، تلال، مزارع، غابات أو مناطق طبيعية بحسب الأصول المتاحة.
- طريق ربط منطقي بين المنطقتين مع انتقال تدريجي في البيئة والإنارة والمرور.
- معالم واضحة تساعد اللاعب على معرفة موقعه دون الحاجة إلى تحميل خرائط خارجية.

### 6.3 هل ندمج عالمين جاهزين؟

يمكن تقنياً استيراد أصول ومناطق من مشاريع مختلفة إذا كانت الملفات والرخص تسمح بذلك، لكن **لا يمكن افتراض أن خريطتين كاملتين ستندمجان تلقائياً**. قبل الدمج يجب فحص:

1. حق الاستخدام والتعديل والتوزيع لكل أصل.
2. نظام الإحداثيات والوحدات والمقياس والارتفاعات.
3. اختلاف الإضاءة والمواد والـPost Process.
4. Collision وNavMesh وطرق المرور.
5. كثافة المجسمات وعدد Draw Calls والذاكرة.
6. تكرار الأصول وتعارض أسماء الملفات والمواد.
7. حدود World Partition والـStreaming والـHLOD.

لا تستخدم ملفات خرائط أو شخصيات أو سيارات مستخرجة من GTA أو Red Dead أو أي لعبة تجارية أخرى. نستعمل أصولاً أصلية أو مرخصة ونبني الإحساس العام دون نسخ المحتوى المحمي.

### 6.4 التوليد الإجرائي

يمكن استخدام **PCG Framework** لتوزيع نباتات وصخور وأعمدة وأشياء بيئية وفق قواعد. التوليد الإجرائي أداة مساعدة، وليس بديلاً عن تصميم الطرق والمباني والمعالم يدوياً. يجب وضع Seed ثابت للنتائج المهمة حتى لا يتغير العالم عشوائياً عند كل بناء.

## 7. الحياة داخل العالم والذكاء الاصطناعي

### 7.1 حركة المرور

- سيارات تسير على مسارات محددة أو شبكة طرق قابلة للملاحة.
- التوقف عند الإشارات والتقاطعات وإعطاء أولوية المرور وفق قواعد بسيطة.
- مسافات آمنة بين المركبات، وتجنب الاصطدامات غير المقصودة.
- استجابة للانسداد وإعادة تخطيط محدودة.
- تقليل عدد السيارات النشطة حسب المسافة وميزانية الأداء.

### 7.2 الشخصيات غير القابلة للعب

- مشاة يسيرون في مناطق مسموح بها.
- نقاط اهتمام وروتين يومي مبسط بدلاً من محاكاة حياة كاملة لكل شخصية.
- تجنب العوائق والتوقف والتفاعل البسيط مع البيئة.
- مستويات LOD سلوكية: سلوك مبسط للشخصيات البعيدة، وسلوك كامل للقريبة.
- عدم تشغيل Tick مكلف لكل شخصية طوال الوقت.

### 7.3 أنشطة اللاعب

- استكشاف العالم.
- قيادة حرة وتجارب زمنية وسباقات خيالية على مسارات مغلقة.
- مهام توصيل أو تصوير أو استكشاف أو مساعدة شخصيات.
- شراء/تخصيص المركبات أو فتحها عبر التقدم إن كانت هذه الأنظمة ضمن النطاق.

## 8. الطقس والوقت والبيئة

- دورة نهار وليل يمكن التحكم بسرعة مرورها.
- حالات طقس: صافٍ، غائم، مطر خفيف، مطر قوي، ضباب؛ العواصف خيار لاحق.
- انتقال تدريجي بين حالات الطقس، وليس تبديل فجائي غير مبرر.
- تغيير اتجاه وشدة الإضاءة والظلال والسماء.
- صوت المطر والرياح والطيور وحركة المدينة بحسب المنطقة والوقت.
- أسطح مبللة تدريجياً وانعكاسات وبرك ماء عند وجود ميزانية أداء مناسبة.
- أصوات داخل مقصورة السيارة تختلف عن الأصوات خارجها.

## 9. الصوت

- طبقات صوت للمحرك تعتمد على RPM والحمل.
- أصوات إطارات مختلفة حسب الطريق والسرعة.
- خطوات تتغير حسب السطح.
- أصوات مدينة وريف ومناطق داخلية وخارجية.
- صوت المطر والرياح والرعد إن أضيف.
- إعدادات مستقلة للموسيقى والمؤثرات والحوار والواجهة.
- كل ملف صوتي يجب أن يكون أصلياً أو مرخصاً؛ لا تنسخ موسيقى أو أصوات ألعاب معروفة.

## 10. واجهة المستخدم

- شاشة بداية، متابعة، لعبة جديدة، إعدادات، خروج.
- قائمة إيقاف مؤقت تعمل Offline.
- HUD قيادة واضح وغير مزدحم.
- خريطة مصغرة أو خريطة عالم محلية لاحقاً.
- إعدادات الرسوم والتحكم والصوت واللغة.
- إعادة تعيين أزرار التحكم.
- ترجمة عربية سليمة، مع دعم اتجاه RTL في القوائم والنصوص.
- لا تضع أزراراً شكلية؛ كل عنصر ظاهر يجب أن يكون مرتبطاً بوظيفة حقيقية أو موسوماً بوضوح بأنه غير متاح أثناء التطوير.

## 11. الحفظ والعمل دون إنترنت

- استخدام نظام **SaveGame** المحلي في Unreal.
- حفظ مكان اللاعب، آخر مركبة/حالة مستخدمة، التقدم، الإعدادات، المركبات المفتوحة، والمهام.
- نسخ احتياطية أو ملفات حفظ متدرجة لتقليل فقدان البيانات.
- رقم إصدار لبنية ملف الحفظ مع مسار ترقية عند تغيير الحقول.
- اختبار بدء اللعبة مع قطع اتصال الإنترنت بالكامل.
- منع أي خدمة خارجية من أن تكون شرطاً لتشغيل العالم أو تحميل الحفظ.
- لا يوجد Multiplayer أو حساب مستخدم أو Cloud Save في النسخة الأولى.

## 12. الأداء والعتاد — Android أولاً

### 12.1 متطلبات منصة التطوير مقابل متطلبات هاتف اللاعب

توصيات Epic الخاصة بمحطة تطوير Unreal على Windows (مثل 32GB RAM و8GB VRAM أو أكثر) تخص جهاز التطوير ولا تعني أن هذه هي مواصفات هاتف اللاعب. بالنسبة إلى Android، توثق صفحة Unreal Engine 5.8 دعماً لأجهزة Android 8 أو أحدث، ومعالج Arm 64-bit، ووحدات GPU متوافقة وواجهات OpenGL ES 3.2 أو Vulkan 1.1 على الأجهزة والتعريفات المناسبة. هذه حدود توافق للمحرك وليست وعداً بأن لعبة عالم مفتوح كبيرة ستعمل بسلاسة على كل جهاز يطابقها.

توثق صفحة UE 5.8 إعداد Android باستخدام Android SDK/NDK وJava، وتشير إلى target SDK 35، وNDK r27c، وBuild-tools 35.0.1، وJava 21.0.3 في صفحة Quick Start وقت إعداد هذه الوثيقة. يجب إعادة فحص المتطلبات الرسمية عند بناء الإصدار النهائي لأن متطلبات Android والمتاجر قد تتغير.

### 12.2 أهداف قياس لا وعود

- 30 FPS تعادل تقريباً 33.33ms لكل إطار.
- 40 FPS تعادل 25ms لكل إطار.
- 60 FPS تعادل تقريباً 16.67ms لكل إطار.
- 90 FPS تعادل تقريباً 11.11ms لكل إطار.
- 120 FPS تعادل تقريباً 8.33ms لكل إطار.
- للهواتف، يكون الهدف الأول ثبات 30 أو 40 FPS على فئة الأجهزة التي نحددها بعد معرفة العتاد، ثم 60 FPS على الأجهزة الأقوى؛ 90/120 FPS خيارات متقدمة وليست وعداً عاماً.
- لا نعلن FPS دون قياس على هاتف فعلي، وبناء محدد، وإعدادات ومنطقة اختبار محددة.

### 12.3 أدوات القياس

- Unreal Insights لقياس CPU والذاكرة والتوقيت.
- `stat unit` و`stat gpu` ومقاييس المحرك المناسبة.
- `ProfileGPU` عند تحليل عنق زجاجة الرسوم.
- اختبار نفس مسار القيادة ونفس الطقس ونفس عدد الشخصيات للمقارنة بين Builds.
- قياس أوقات تحميل الخلايا ووقت فتح اللعبة والذاكرة أثناء جلسة طويلة.

### 12.4 ما لا نعرفه بعد

لا توجد مواصفات هاتف المستخدم في هذه الوثيقة. لذلك لا يمكنني تحديد أقل هاتف مستهدف أو إعدادات الرسوم أو FPS المتوقع. يلزم طراز الهاتف، المعالج/SoC، GPU، RAM، دقة الشاشة ومعدل تحديثها وإصدار Android قبل تحديد فئة دعم واقعية. لا نختلق أرقام أداء أو ضمانات توافق.

## 15. خطة الاختبار الإلزامية

### 15.1 اختبارات وظيفية

1. تشغيل اللعبة دون اتصال بالإنترنت.
2. بدء لعبة جديدة ثم إيقافها وإعادة تحميل الحفظ.
3. المشي والجري والقفز والتوقف وتغيير الاتجاه على أرض مستوية ومنحدر ودرج.
4. دخول السيارة والخروج منها مرات متكررة دون تعليق أو اختراق Collision.
5. القيادة والفرملة والرجوع والتوجيه على كل سطح.
6. اختبار المطر والسطح المبلل ومقارنة السلوك مع السطح الجاف.
7. تحميل منطقة جديدة وتفريغ منطقة قديمة دون فقد اللاعب أو المركبة.
8. حفظ الإعدادات واللغة والتحكم بعد إعادة التشغيل.
9. اختبار الواجهة بدقة شاشة مختلفة وبنسب عرض مختلفة.
10. اختبار جلسة طويلة لرصد تسرب الذاكرة أو تدهور الأداء.

### 15.2 أنواع الاختبارات

- C++ Unit Tests للمنطق القابل للاختبار منفصلاً.
- Unreal Automation Tests لاختبارات الوحدة والميزات والمحتوى.
- Functional Tests لاختبارات مستويات اللعب والسلوك.
- Smoke Tests سريعة عند كل تغيير أساسي.
- Content Stress Tests لتحميل الخرائط وتجميع Blueprints وفحص المحتوى.
- Screenshot Comparison عند توفر صور حقيقية ملتقطة من Build متطابق الإعدادات.

### 15.3 قواعد إعلان النجاح

- لا تكتب PASS لأن الكود يبدو صحيحاً.
- لا تعتبر نجاح Compile دليلاً على نجاح Gameplay.
- لا تعتبر Screenshot من المحرر دليلاً على أن Build يعمل.
- كل نتيجة تتضمن الأمر الذي نُفّذ، البيئة، رقم الـBuild، السجل، والنتيجة.
- عند عدم توفر Unreal Engine أو عتاد مناسب، اكتب `NOT RUN` مع السبب؛ لا تستبدلها بـPASS.
- عند فشل اختبار، احتفظ بالسجل وأصلح السبب ولا تحذف الاختبار لتصبح النتيجة خضراء.

هذا الملحق يضيف متطلبات المستخدم الجديدة، ويعدّل أولوية المنصة إلى Android. إذا تعارض أي افتراض سابق في الوثيقة مع هذا الملحق، تكون الأولوية لهذا الملحق فيما يخص منصة التسليم والأداء على الهاتف.

## 20. هوية المطوّر وشاشة البداية

- يظهر اعتماد المطوّر بالنص العربي المطابق تماماً: **«تطوير: عبدالله لازم»**.
- يظهر الاعتماد في بداية تشغيل اللعبة ضمن شاشة البداية/شعار المطوّر، بخط عربي واضح وتباين مناسب، ولا يُنسب العمل إلى شخص آخر.
- تكون شاشة البداية قصيرة وغير مزعجة، ثم تنتقل إلى القائمة الرئيسية؛ يمكن السماح بتجاوز المقدمة بعد ظهور الاعتماد، مع عدم إلغاء ظهور الاعتماد من الإصدار النهائي.
- لا يُنشأ شعار رسومي نهائي من دون ملف تصميم حقيقي أو قرار تصميم معتمد. في المرحلة الأولى يكفي عرض النص بتنسيق واجهة أصلي؛ لا تدّعِ وجود صورة شعار غير موجودة.
- يُسجّل اسم المطوّر داخل صفحة Credits في الإعدادات/القائمة أيضاً.

## 21. Android APK هو هدف التسليم الأساسي

### 21.1 المنصة وإعداد التغليف

- منصة الإطلاق الأساسية: Android 64-bit، مع حزمة `arm64-v8a`.
- المنتج المطلوب للمستخدم: ملف تثبيت APK قابل للتثبيت يدوياً والعمل دون إنترنت. إذا تطلب حجم المحتوى إخراج OBB أو ملفات بيانات إضافية بحسب إعداد Unreal، يجب تسليمها وشرح مكانها؛ لا تقل إن APK وحده مكتفٍ إذا لم يكن ذلك صحيحاً.
- يجب أن يحتوي الإصدار على اسم حزمة فريد، رقم إصدار/Build واضح، أيقونة فعلية، شاشة بداية فعلية، وتوقيع Release. لا تخزن keystore أو كلمات مروره أو مفاتيح التوقيع في Git أو داخل نصوص المحادثة.
- استهدف `arm64-v8a` أولاً لتقليل حجم الحزمة وتعقيد الاختبارات. لا تضف ABI أخرى إلا إذا قرر المشروع دعمها واختبرها.
- فعّل وضع Mobile وScalable عند إنشاء المشروع، واختر Mobile Deferred أو Mobile Forward بناءً على اختبارات الأجهزة؛ لا تستخدم Desktop Renderer لكل الهواتف.
- احتفظ بإعدادات تطوير منفصلة عن إعداد Shipping. لا تشحن Debug overlays أو أوامر المطور أو سجلات حساسة في النسخة النهائية.
- لا تضف Google Play Services أو SDK إعلانات أو Analytics أو API شبكة لمجرد أنها متاحة؛ اللعبة Offline ولا تحتاجها في النسخة الأساسية.
- راجع Android Manifest والأذونات النهائية. لا تطلب صلاحيات غير لازمة، ولا تطلب INTERNET إذا لم يوجد سبب تقني معلن ومقبول.

### 21.2 Toolchain موثق لخط الأساس UE 5.8

وفق صفحة Android Quick Start الخاصة بـUnreal Engine 5.8 وقت تحرير الملحق، تشمل القيم المنشورة: Android 8 أو أحدث، CPU من نوع Arm 64-bit، Android SDK target 35، أدنى SDK للتثبيت 26، NDK r27c، Build-tools 35.0.1، وOpenJDK 21.0.3. كما تسرد واجهات OpenGL ES 3.2 وVulkan 1.1 على Android 10 أو أحدث مع تعريفات متوافقة. هذه بيانات تخص توافق المحرك وسلسلة البناء، وليست مواصفات أداء دنيا مضمونة للعبتنا. يجب إعادة التحقق من وثائق Epic ومتطلبات Google Play قبل كل إصدار.

## 22. الأداء والذاكرة: حمّل ما يحتاجه المشهد فقط

**المبدأ:** لا تحمّل العالم المفتوح كله إلى الذاكرة عند بدء اللعبة. اعمل بنظام Streaming وتفاصيل متدرجة وميزانية موارد محددة لكل فئة جهاز.

### 22.1 إدارة العالم والظهور

- استخدم World Partition أو نظام تقسيم مناطق مناسب لإصدار Android المستهدف، مع اختبار عملي على جهاز حقيقي؛ لا تفترض أن حجم عالم PC نفسه مناسب للهاتف.
- حمّل الخلايا القريبة من اللاعب/الكاميرا وما يحتاجه المسار المتوقع فقط، وابدأ تحميل الخلايا المجاورة مسبقاً حسب اتجاه الحركة وسرعة السيارة لتقليل ظهور العناصر فجأة.
- أزل أو أفرغ الأصول البعيدة غير اللازمة بعد التأكد من عدم استخدامها في الحفظ أو التصادم أو المنطق النشط.
- استخدم Frustum Culling وOcclusion Culling وDistance Culling وLOD وHLOD حيث تناسب الأصل والجهاز.
- استخدم نسخاً بعيدة منخفضة التفاصيل للمباني والأشجار والمركبات، وخفّض كثافة التفاصيل تدريجياً مع المسافة.
- قلّل تحديثات الأنظمة البعيدة: الشخصيات والمرور البعيدان يستخدمان محاكاة مبسطة أو تحديثاً متقطعاً، بينما التفاصيل الكاملة تُستخدم حول اللاعب فقط.
- لا توقف كل ما هو خارج الشاشة بصورة عمياء: يجب إبقاء المناطق المجاورة اللازمة للتحميل والتصادم والملاحة والمرور المباشر فعالة. الهدف هو محاكاة متدرجة لا عالم ينكسر عند النظر بعيداً.
- استخدم Async Loading وTexture Streaming وObject Pooling عند ملاءمتها، وتجنب إنشاء/حذف أعداد كبيرة من الكائنات في الإطار نفسه.
- لا تحمّل أصوات ومؤثرات ومجسمات كل منطقة دفعة واحدة. حمّل الصوت والمواد والـVFX عند الحاجة مع منع الانقطاع الصوتي المفاجئ.

### 22.2 حدود الذاكرة والمعالج والحرارة

- لا تخصص الذاكرة المتاحة كلها للعبة، ولا تخزن بيانات العالم بالكامل في RAM. ضع ميزانية ذاكرة لكل Device Profile وراقب الذاكرة الفعلية للعملية وذاكرة GPU على هواتف الاختبار.
- لا تضع رقماً ثابتاً لحد RAM قبل اختيار الهواتف المستهدفة وقياس الذاكرة؛ يجب تحديد الميزانيات من اختبارات فعلية، مع هامش للنظام وواجهة Android والتطبيقات الأخرى.
- تجنب Tick غير الضروري. استخدم تحديثات مؤقتة أو أحداثاً عند الحاجة، وقلل تكرار الحسابات للشخصيات والأشياء البعيدة.
- استخدم Animation Budget Allocator أو تقنيات مماثلة لتقليل تحديث الرسوم الهيكلية البعيدة حيث تكون متوافقة ومفيدة.
- راقب حرارة الهاتف واستهلاك البطارية وتراجع الأداء بعد جلسات طويلة. عند ارتفاع الحرارة، خفّض الدقة الداخلية أو الظلال أو عدد الشخصيات/السيارات النشطة تدريجياً بدلاً من ترك الهاتف يختنق حرارياً.
- استخدم ضغط الخامات المناسب للجهاز (مثل ASTC أو ETC2 عند الدعم) وأحجام Mip Maps مناسبة. لا تحمل Texture بدقة أعلى من الحاجة البصرية على شاشة الهاتف.
- قلّل الشفافية وOverdraw والمؤثرات ذات كلفة البكسل العالية، وراجع Draw Calls وعدد المضلعات من زاوية الكاميرا الفعلية على الهاتف.
- استخدم Device Profiles وScalability لتطبيق إعدادات مختلفة حسب فئة الجهاز، مع عدم الاعتماد على اسم هاتف واحد فقط لتحديد كل الإعدادات.

### 22.3 الواقعية ضمن حدود الهاتف

- الأولوية للانسيابية والثبات والإحساس الواقعي، وليس لتفعيل كل مؤثر PC على الهاتف.
- استخدم PBR محسّناً للهاتف، Lightmaps/Static Lighting وReflection Captures حيث تناسب المشهد، وسماء وإضاءة ومواد مصممة لتبدو طبيعية بكلفة قابلة للضبط.
- لا تجعل Lumen شرطاً لنسخة Android العامة. وثائق Epic تصف Lumen على Android بأنه دعم تجريبي لأجهزة Android عالية الأداء المتوافقة مع Vulkan SM5 عند استخدام Desktop Renderer، وتذكر أن كلفة Desktop Renderer وLumen مرتفعة وأن Epic لا توصي بشحنه حالياً. يمكن اختبار ملف تجريبي لأجهزة محددة فقط، ولا يدخل النسخة المستقرة قبل إثبات الأداء والحرارة.
- لا تفترض أن Nanite أو Hardware Ray Tracing متاحان أو مناسبان لكل هاتف. استخدم LOD meshes تقليدية كمسار أساسي، ولا تفعّل ميزة متقدمة إلا بعد إثبات دعم الجهاز والمحرك لها.
- اختر ميزات Mobile Deferred أو Forward وSSAO/SSR/decals/post-process على أساس الدعم والكلفة. لا تفرض Bloom أو Motion Blur أو Depth of Field على كل الهواتف؛ اجعل المؤثرات المكلفة اختيارية أو مخففة.
- يمكن استخدام إضاءة وخامات وانعكاسات baked ومؤثرات جوية مبسطة لتحقيق جودة بصرية جيدة دون استهلاك مماثل لنسخة PC.

## 24. شاشة إعدادات FPS — أرقام حقيقية لا شكلية

### 24.1 خيارات حد الإطارات

اعرض قائمة خيارات ممكنة مثل: `تلقائي`، `30`، `40`، `45`، `60`، `90`، `120 FPS`. لا تعرض أو تتيح اختيار معدل لا يدعمه معدل تحديث شاشة الجهاز أو نظام Frame Pacing؛ أخفِ الخيار أو عطّله مع توضيح السبب.

### 24.2 فصل ثلاثة أرقام مختلفة

يجب ألا تخلط الواجهة بين:

1. **حد FPS المختار (Frame Cap):** أعلى عدد إطارات تسمح اللعبة بمحاولة تقديمه.
2. **FPS الحالي المقاس:** معدل الإطارات الفعلي الذي تحققه اللعبة في اللحظة/متوسط نافذة زمنية قصيرة.
3. **معدل تحديث الشاشة (Refresh Rate):** ما تدعمه شاشة الهاتف مثل 60Hz أو 90Hz أو 120Hz.

مثال توضيحي فقط: إذا اختار اللاعب حد 120 FPS لكن الجهاز يعالج المشهد فعلياً عند 40 FPS، فسوف يبقى العرض المقاس قرابة 40 FPS وليس 120. اختيار حد 120 لا يصنع أداءً غير موجود ولا يضمن الوصول إليه. وإذا كانت الشاشة نفسها لا تدعم 120Hz، فلا ينبغي عرض 120 كخيار قابل للتطبيق.

### 24.3 التنفيذ الفني

- استخدم Android Swappy Frame Pacing المدمج في Unreal Engine، وهو مفعّل افتراضياً في UE 5.2 وما بعده بحسب وثائق Epic، ما لم يثبت الاختبار أن إعداداً آخر مطلوب.
- استخدم `FPlatformRHIFramePacer::SupportsFramePace` للتحقق من توافق خيار الإطارات، و`SetFramePace` لتطبيقه، و`GetFramePace` لقراءة الحد الحالي؛ أو استخدم إعداد `r.setframepace` بالطريقة الموثقة المناسبة للإصدار.
- افحص أوضاع الشاشة ومعدل تحديثها الفعلي قبل تمكين 60/90/120. لا تفترض أن كل هاتف يعرض 120Hz.
- قِس FPS الحالي من زمن الإطار الفعلي، واعرض متوسطاً ملساً على نافذة زمنية معلنة، مع عدم تزوير الرقم أو تثبيته على القيمة المختارة.
- يمكن تفعيل خيار تلقائي يختار أعلى حد مستقر بعد قياس مشهد لعب ممثل، مع هامش أمان ومراقبة الحرارة؛ لا تستنتج الحد الأقصى من اسم المعالج وحده.
- إذا تعذر القياس أو لم تتوفر واجهة موثوقة، اعرض «جارٍ القياس» أو «غير متاح» ولا تعرض رقماً مختلقاً.
- لا ترفع أولوية المعالج أو تستهلك البطارية والحرارة بلا داعٍ فقط لملاحقة رقم 120.
- احفظ اختيار اللاعب محلياً، وأعد التحقق عند تغيير الجهاز أو وضع الشاشة أو بعد تحديث اللعبة.

## 25. واجهة التحكم باللمس

- تصميم Landscape افتراضياً للقيادة والعالم المفتوح، مع احترام النتوءات ومناطق الأمان ونسب الشاشات المختلفة.
- عصا حركة افتراضية للشخصية، وأزرار تفاعل/قفز/ركض حسب تصميم اللعب، وأزرار توجيه وتسارع وفرامل للمركبة.
- تغيير تخطيط الأزرار وحجمها وشفافيتها ومواقعها، مع زر لإعادة الإعدادات الافتراضية.
- زر واضح للدخول والخروج من السيارة يظهر فقط عندما يكون التفاعل صالحاً.
- لا تزدحم الشاشة بعناصر كثيرة؛ أخفِ أزرار المشي أثناء القيادة والعكس.
- اجعل اللمس قابلاً للاستخدام بيد واحدة أو يدين وفق نمط التحكم، مع استجابة لمسية مستقرة وتجنب تسجيل الضغط مرتين.
- دعم Gamepad اختياري، لكن لا يشترط وجوده لتشغيل اللعبة.

## 26. اختبارات القبول الإضافية لنسخة الهاتف

1. بناء Android Shipping حقيقي لـarm64-v8a، وتسجيل إصدار Unreal وSDK/NDK وCommit ورمز خروج البناء.
2. تثبيت APK على هاتف فعلي وتشغيله بعد إعادة تشغيل الجهاز.
3. تشغيل اللعبة في وضع الطيران والتأكد من أن الشاشة الرئيسية واللعب والحفظ والتحميل والموسيقى لا تتطلب الإنترنت.
4. التحقق من ظهور «تطوير: عبدالله لازم» في بداية اللعبة وصفحة Credits.
5. فحص أن القائمة لا تحمل خريطة العالم كاملة ولا تستهلك ذاكرة كبيرة بلا داعٍ.
6. تشغيل مسار ثابت يتضمن المشي وركوب السيارة والقيادة والانتقال بين منطقتين، وقياس CPU/GPU/RAM/FPS ووقت تحميل الخلايا.
7. قياس FPS الحالي مقابل حد الإطارات ومعدل تحديث الشاشة. اختبر خيار 120 فقط على جهاز وشاشة يدعمانه، ولا تعتبر اختيار 120 نتيجة نجاح إذا لم يكن FPS الفعلي قريباً منه.
8. اختبار أجهزة بمعدلات شاشة مختلفة، مثل 60Hz و90Hz و120Hz إذا توفرت؛ سجّل الطراز الفعلي لكل جهاز ولا تدّعِ اختبار أجهزة غير متوفرة.
9. اختبار جلسة مستمرة لا تقل عن 30 دقيقة لرصد ارتفاع الحرارة، خفض الأداء، الذاكرة، واستهلاك البطارية.
10. اختبار انتقال الخلايا دون تقطيع شديد أو اختفاء مفاجئ للتصادم أو ظهور اللاعب داخل عناصر العالم.
11. اختبار تدوير الشاشة/قفل الوضع الأفقي، مناطق الأمان، أحجام الواجهة، واللمس المتعدد.
12. عند فشل جهاز في هدف FPS، سجّل الاختناق CPU أو GPU أو Memory أو Thermal وخفّض الجودة المناسبة؛ لا ترفع رقم FPS في الواجهة ولا تخفي الفشل.
13. سجّل نتائج كل جهاز في `Docs/ANDROID_DEVICE_TEST_MATRIX.csv` متضمنة الطراز، Android، SoC، GPU، RAM، الشاشة/Hz، إعداد الرسوم، حد FPS، FPS المقاس، حرارة البداية/النهاية، الذاكرة، مدة الاختبار والنتيجة.

# 29. أمر التنفيذ الإلزامي لوكيل AI — لا تكتفِ بالخطة أو الهيكل الفارغ

هذا القسم هو تعليمات تنفيذ مباشرة للوكيل الذي سيعمل على مستودع اللعبة. يُقرأ مع كامل الوثيقة من البداية إلى النهاية. **المطلوب تنفيذ المشروع فعلياً داخل المستودع المتاح، وليس إعادة صياغة المواصفات أو إنشاء قائمة مهام فقط.** استخدم قدرات البيئة والأدوات المتاحة فعلاً، وأنشئ ملفات المشروع والأنظمة والاختبارات والوثائق اللازمة، ثم ابنِ واختبر ما تسمح به البيئة.

## 29.1 تكليف الوكيل والنتيجة المطلوبة

أنت مهندس Unreal Engine 5 ومهندس Android ومختبر برمجيات. مهمتك إكمال أكبر قدر ممكن من لعبة العالم المفتوح المحددة في هذه الوثيقة إلى مشروع متماسك قابل للبناء والتشغيل، مع إعطاء الأولوية للنسخة Android arm64-v8a وللأداء والسلاسة والواقعية واللعب دون إنترنت.

لا تعتبر إنشاء مجلدات أو ملفات C++ فارغة أو Widgets شكلية أو أزراراً لا تعمل أو خريطة فارغة أو APK غير مثبت دليلاً على اكتمال اللعبة. كل ميزة يجب أن تكون موصولة بسير عمل اللعبة، ومختبرة بقدر ما تسمح البيئة، وموثقة بحالة صادقة.

ابدأ بفحص حالة المستودع والبيئة. إذا كان هناك مشروع قائم، أكمله ولا تستبدله بمشروع جديد. إذا لم يوجد مشروع، أنشئ مشروع Unreal مناسباً داخل المستودع. لا تتوقف بعد التحليل أو كتابة الخطة؛ ابدأ بالتنفيذ، وواصل دورات البناء والفحص والإصلاح حتى تنجح معايير القبول أو يظهر مانع حقيقي موثق.

## 29.2 قاعدة الصراحة: لا يمكن ضمان انعدام كل الأخطاء مطلقاً

الهدف هو تسليم إصدار **بلا أخطاء معروفة مانعة للإصدار**، مع تصفير أخطاء البناء والاختبارات والانهيارات التي يمكن فحصها. لا يحق لك أن تعد المستخدم بأن لعبة بهذا الحجم خالية من كل خطأ محتمل على كل هاتف. لا تخفِ هذا القيد، ولا تحوّل عدم القدرة على الاختبار إلى PASS.

استخدم حالات موحدة لكل مطلب واختبار:

- `PASS`: نُفّذ الاختبار فعلياً ونجح، ويوجد دليل واضح.
- `FAIL`: نُفّذ الاختبار وفشل؛ يجب إصلاحه وإعادة الاختبار.
- `BLOCKED`: تعذر التنفيذ بسبب مانع خارجي محدد، مثل غياب Unreal Engine أو Android SDK/NDK أو جهاز Android فعلي.
- `NOT RUN`: لم يُنفّذ الاختبار بعد.
- `NOT APPLICABLE`: لا ينطبق مع شرح موجز.

لا تستخدم `PASS` بناءً على قراءة الكود فقط إذا كان المطلوب اختباراً تشغيلياً. لا تضع نتائج FPS أو حرارة أو استهلاك RAM أو صور لعب أو سجل جهاز غير موجود. لا تكتب أن APK جرى تثبيته أو اختباره دون سجل يثبت ذلك.

## 29.3 المرحلة صفر — جرد آمن قبل التعديل

نفّذ وسجّل هذه الخطوات أولاً:

1. اعرض المسار الحالي، نظام التشغيل، إصدار Unreal إن كان مثبتاً، إصدار compiler، Java، Android SDK/NDK، Gradle إن كان مطلوباً، وأدوات البناء المتاحة.
2. افحص المستودع: `git status`, الفرع الحالي، آخر commit، الملفات المعدلة وغير المتعقبة، وحجم المجلدات.
3. افحص كل ملفات المشروع الحالية والـ`.uproject` والـ`.uplugin` وملفات `Config` و`Source` و`Content` و`Plugins` و`Build` و`scripts` و`Tests` والوثائق.
4. لا تحذف أو تستبدل أو تنقل ملفات المستخدم لمجرد أن أسماءها غير مألوفة. لا تستخدم `git reset --hard` أو `git clean -fdx` أو force push أو حذفاً جماعياً. لا تكتب فوق تغييرات غير محفوظة.
5. أنشئ جرداً أولياً يحدد ما هو موجود وما هو ناقص، ومخطط تبعيات أولي.
6. إذا كانت هناك تغييرات مستخدم غير ملتزمة، احفظها كما هي واعمل حولها. لا تنفّذ commit أو push إلا إذا طلب المستخدم ذلك صراحة.

إذا لم تتوفر الأدوات المطلوبة، لا تتظاهر بوجودها. نفّذ ما يمكن تنفيذه، وسجّل اسم الأداة الناقصة ورسالة التحقق والأثر المحدد على التسليم.

## 29.4 المرحلة الأولى — بنية مشروع مترابطة وقابلة للصيانة

أنشئ أو راجع بنية مشروع واضحة، ولا تنشئ نسخاً متضاربة من النظام نفسه. على الأقل، يجب أن تكون المسؤوليات معروفة ومترابطة:

- `Source/`: وحدات C++ والأنظمة الأساسية.
- `Content/`: الخرائط والشخصيات والمركبات والمواد والأصوات والواجهات وبيانات اللعبة.
- `Config/`: إعدادات المحرك والمنصات والإدخال والرسوم والحفظ.
- `Plugins/`: الإضافات الضرورية فقط، مع تثبيت نسخها وتوثيق مصدرها ورخصتها.
- `Build/` أو إعدادات البناء المعتمدة: إعدادات Android والتغليف.
- `Scripts/`: سكربتات البناء والتحقق والتجهيز، مع توثيق طريقة تشغيلها.
- `Tests/`: اختبارات آلية واختبارات قبول وسيناريوهات تشغيل.
- `Docs/`: المعمارية وسجل البناء والاختبارات والتراخيص والمشكلات المعروفة.

لا تتعامل مع هذه الأسماء على أنها إلزامية حرفياً إذا كان المشروع القائم يستعمل تنظيماً سليماً آخر؛ المهم أن تكون المسارات الفعلية موثقة وصحيحة.

### فحص ربط الملفات والمراجع

يجب تنفيذ فحص آلي للمراجع والمسارات، ويشمل بحسب ما ينطبق:

1. كل ملف يذكره ملف إعداد أو سكربت أو وثيقة تسليم يجب أن يكون موجوداً في المسار الصحيح، أو يُذكر بوضوح أنه يُنشأ في مرحلة لاحقة.
2. كل Module في `.uproject` أو `.uplugin` يجب أن يقابل تعريف Module صحيحاً وملفات Build صحيحة.
3. كل Plugin مطلوب يجب أن يكون موجوداً ومفعلاً ومتوافقاً مع نسخة المحرك؛ لا تترك Plugin مفقوداً أو اعتماداً اختيارياً مفعلاً بلا سبب.
4. كل `#include` واسم Class واسم Module واعتماد في `*.Build.cs` يجب أن يحلّ إلى ملف/وحدة موجودة. افحص الاعتماديات الدائرية أو غير الضرورية.
5. افحص مراجع الخرائط الافتراضية وخرائط Game/Editor وGameMode وPawn وPlayerController وHUD/Input Mapping Context وواجهات المستخدم.
6. افحص مسارات الأصول ومراجع Soft/Hard References وPrimary Asset Labels وAsset Manager وRedirectors، وتأكد من أن الأصول المطلوبة للتشغيل تصل إلى الحزمة ولا تُستبعد خطأً.
7. افحص أن أسماء الخرائط والأصول في إعدادات التغليف تطابق ملفاتها الفعلية، وأن المسارات لا تعتمد على مسار مطلق خاص بجهاز المطور.
8. افحص مسارات الحفظ وملفات الإعدادات والصلاحيات على Android، ولا تستخدم مجلدات غير قابلة للكتابة.
9. افحص روابط الأوامر: كل سكربت يستدعي سكربتاً آخر يجب أن يشير إلى مسار صحيح، ويمرر الوسائط الصحيحة، ويتعامل مع رمز الخروج. لا تسمح لسكربت أن يطبع نجاحاً بعد فشل أمر داخلي.
10. افحص ملفات Workflow/CI ومصفوفات البناء: لا تستدعِ ملفاً غير موجود، ولا تفترض متغير بيئة أو Secret غير معرف. لا تطبع الأسرار في السجلات.

أنشئ تقريراً مثل `Docs/FILE_AND_DEPENDENCY_AUDIT.md` يسرد المسارات والوحدات والإضافات والخرائط وسكربتات البناء والروابط، مع نتيجة كل فحص.

## 29.5 المرحلة الثانية — التنفيذ الوظيفي وليس الواجهات الوهمية

نفّذ المزايا بهذا الترتيب، مع الحفاظ على ترابطها:

1. تشغيل التطبيق، شاشة البداية، اسم المطور «تطوير: عبدالله لازم»، القائمة الرئيسية، الإعدادات، والاعتمادات.
2. بدء لعبة جديدة/متابعة، إنشاء SaveGame، الحفظ والتحميل واستعادة الإعدادات بعد إغلاق التطبيق.
3. شخصية قابلة للتحكم باللمس، كاميرا، حركة أساسية واستجابة إدخال سليمة.
4. مركبة قابلة للقيادة، توجيه وتسارع وفرامل واحتكاك وتعليق، ثم الدخول والخروج منها والانتقال بين أنظمة التحكم.
5. خريطة اختبار صغيرة مكتملة، مع تصادمات وحدود واضحة ونقاط Spawn وNavigation عند الحاجة.
6. تحميل وتفريغ أجزاء البيئة تدريجياً، واختبار الانتقال بين الخلايا وعدم سقوط اللاعب أو ظهور فراغات أو فقدان التصادم.
7. أنظمة الطقس والليل والنهار والصوت والمؤثرات بعد ثبات الحركة والقيادة.
8. المرور وNPC والأنشطة بعد وضع حدود صارمة لعدد الكيانات البعيدة وتحديثها.
9. توسيع الخريطة إلى المدينة والريف بعد إثبات الأداء في شريحة لعب متصلة.
10. تحسين الرسوم والأداء وإعدادات الجهاز، ثم التغليف والتثبيت والاختبار النهائي.

كل زر أو تفاعل ظاهر في النسخة المسلّمة يجب أن يعمل. إذا لم تُنفذ ميزة، لا تعرضها للمستخدم على أنها موجودة. لا تضع زر متجر أو أونلاين أو Multiplayer في نسخة Offline إذا لم تكن وظيفته متاحة.

## 29.6 المرحلة الثالثة — دورة بناء وإصلاح لا تتوقف عند أول فشل

نفّذ حلقة العمل التالية بصورة متكررة:

1. شغّل فحص التنسيق والتحليل الساكن وفحوص ملفات الإعداد.
2. ابنِ وحدات C++ ومشروع Editor/Development بحسب البيئة.
3. عالج أخطاء الترجمة والربط والـUHT والـUAT وملفات Build.cs وPlugins.
4. شغّل اختبارات الأتمتة واختبارات الوظائف الأساسية.
5. شغّل المشروع أو اختباراً Headless/Automation صالحاً حيث تسمح البيئة.
6. افحص السجلات بحثاً عن `Error`, `Fatal`, `Ensure`, `Assertion`, Missing Package, Failed to Load, unresolved symbol, missing module وأخطاء Android.
7. أصلح السبب الجذري، لا تخفِ الخطأ بتعطيل الاختبار أو إسكات السجل أو إزالة الميزة المطلوبة.
8. أعد الاختبار المتأثر، ثم أعد مجموعة الاختبارات ذات العلاقة واختبار الانحدار.
9. احفظ سجل كل محاولة ونتيجتها ورمز خروج الأمر وملفات السجل.

إذا فشل البناء، لا تنتقل إلى تقرير نهائي يوحي بالاكتمال. استمر في الإصلاح ما دام السبب قابلاً للمعالجة ضمن البيئة. إذا وصل العمل إلى مانع خارجي لا يمكن تجاوزه، أوقف الادعاء بالنجاح، ووثق المانع والخطوة الوحيدة اللازمة لرفعه.

لا تستخدم أوامر غير مفهومة أو أوامر من الإنترنت دون فحص مصدرها. قبل أي أمر قد يحذف أو يستبدل ملفات، اشرح أثره وتجنب تنفيذه ما لم يكن ضرورياً ومأذوناً. لا تستخدم ملفات APK أو أصولاً مجهولة المصدر.

## 29.7 مصفوفة اختبارات إلزامية

أنشئ اختبارات آلية حيث يمكن ذلك، واختبارات يدوية موثقة عندما تتطلب لمساً أو جهازاً حقيقياً. يجب أن تغطي المصفوفة على الأقل:

| المجال | الاختبار المطلوب | دليل النجاح |
|---|---|---|
| فتح المشروع | فتح `.uproject` بالنسخة المحددة دون Module/Plugin مفقود | سجل Editor أو Build نظيف |
| البناء | بناء الهدف المطلوب دون Compile/Link errors | سجل بناء ورمز خروج 0 |
| الإقلاع | تشغيل اللعبة والوصول إلى القائمة | سجل تشغيل أو فيديو/لقطة حقيقية |
| القائمة | تجربة كل زر ظاهر | نتائج اختبار لكل زر |
| المطور | ظهور «تطوير: عبدالله لازم» في المواضع المحددة | لقطة فعلية |
| Offline | تشغيل وضع الطيران دون فشل | سجل جهاز فعلي |
| الحفظ | حفظ ثم إغلاق وإعادة تشغيل وتحميل | نتيجة مقارنة الحالة المستعادة |
| الشخصية | مشي/ركض/قفز/كاميرا/تصادم | سيناريو اختبار موثق |
| المركبة | توجيه/تسارع/فرامل/توقف/اصطدام/دخول وخروج | سيناريو اختبار موثق |
| تبديل التحكم | انتقال الشخصية إلى السيارة والعكس دون تكرار الإدخال | اختبار وظيفي |
| العالم | الانتقال بين خلايا التحميل والتفريغ | سجل وعدم وجود سقوط/فراغات/Crash |
| الأداء | CPU/GPU/RAM/FPS ووقت الإطار والحرارة | قياسات من جهاز معلوم |
| الهاتف | تثبيت وفتح APK على جهاز Android حقيقي | طراز الجهاز وسجل التثبيت والتشغيل |
| التغليف | فحص APK والـABI والتوقيع والحجم والملفات | سجل Packaging وفحص الحزمة |
| التراخيص | فحص قائمة كل أصل ومصدره ورخصته | Asset License Manifest |

لا تستبدل اختبار الهاتف الحقيقي باختبار المحاكي ثم تصف النتيجة بأنها اختبار هاتف. يجوز استخدام المحاكي لاختبار الإقلاع والوظائف المبدئية، لكن الأداء والحرارة واللمس الفعلي تتطلب هاتفاً حقيقياً.

## 29.8 فحوص Android وAPK قبل التسليم

- تحقق من `arm64-v8a` وأن الحزمة ليست ABI غير مقصود.
- تحقق من إعدادات Package Name وVersion Name وVersion Code وMinimum SDK وTarget SDK وOrientation والصلاحيات.
- لا تطلب صلاحيات لا تحتاجها اللعبة. لا تضف صلاحية إنترنت ما لم توجد حاجة موثقة؛ يجب أن تعمل التجربة الفردية الأساسية في وضع الطيران.
- افحص ملفات OBB/ملفات البيانات الإضافية إن استُخدمت، وتأكد أن آلية توزيعها واضحة وليست مفقودة من ملف التسليم.
- افحص أن ملفات الصوت والأصول المطلوبة مضمنة أو محمّلة من مسار محلي متاح، ولا توجد روابط ويب إلزامية أثناء اللعب.
- افحص التوقيع والحزمة الناتجة باستخدام أدوات Android المتاحة. لا تستخدم مفاتيح توقيع خاصة بالمستخدم أو تضعها في المستودع. إن كانت نسخة تسليم تجريبية موقعة بمفتاح Debug، اذكر ذلك صراحة ولا تسمها إصدار متجر Production.
- ثبّت APK باستخدام ADB على جهاز الاختبار المتاح، شغّله، راقب Logcat وسجلات اللعبة، ثم اختبر بدء اللعبة واللعب والحفظ وإعادة الفتح.
- احسب SHA-256 للـAPK النهائي، واكتب الحجم والاسم والمسار والهاش في تقرير التسليم.
- لا تسمِّ APK مرشحاً نهائياً إلا بعد اجتياز فحوصه. استخدم تسمية `candidate-unverified` إذا لم يكتمل اختبار الجهاز.

## 29.9 فحوص الأداء والذاكرة ومنع التحميل الشامل

- لا تحمّل العالم كاملاً عند بدء التشغيل. يجب أن تكون القائمة الرئيسية خفيفة ولا تفتح خريطة اللعب بلا حاجة.
- راجع World Partition streaming sources ومسافة التحميل والتفريغ وأولوية الخلايا، وتحقق من وجود اللاعب/السيارة/الكاميرا كمصادر تحميل صحيحة.
- استخدم LOD/HLOD وTexture Streaming وMesh/Material budgets وObject Pooling عند الحاجة، وحدد Cull Distances للكائنات البعيدة.
- خفّض تحديث AI والفيزياء والمؤثرات للكيانات البعيدة، ولا تحدّث كل NPC في كل Frame.
- تجنّب Tick غير الضروري والذاكرة المؤقتة المتزايدة ومراجع الأصول الصلبة غير الضرورية. افحص تسرب الذاكرة على جلسة طويلة.
- قِس زمن الإطار 16.67ms عند 60 FPS و25ms عند 40 FPS و8.33ms عند 120 FPS كأهداف زمنية حسابية، لا كادعاء أن الجهاز حققها.
- اعرض Frame Cap وMeasured FPS وRefresh Rate كقيم منفصلة. لا ترفع عداد FPS برمجياً ولا تعرض الحد المختار بدلاً من القياس.
- اختبر هبوط الأداء بعد ارتفاع حرارة الهاتف، وليس فقط أول دقيقة من التشغيل.
- إن لم يتوفر جهاز حقيقي، اكتب `DEVICE_PERFORMANCE_TEST=BLOCKED`، ولا تدّعِ أن اللعبة سلسة على كل الهواتف.

## 29.10 فحص المحتوى والأصول والصور والصوت

- لا تنسخ خرائط أو سيارات أو شخصيات أو شعارات أو موسيقى GTA أو Forza أو أي لعبة تجارية.
- لكل أصل خارجي، سجّل اسم الأصل، الرابط الدقيق، المؤلف/الناشر، نوع الرخصة، القيود، تاريخ التنزيل، وملف الترخيص أو إثباته في `Docs/ASSET_LICENSE_MANIFEST.csv`.
- إذا لم تتأكد من رخصة الأصل، لا تضعه في إصدار التوزيع. استبدله بأصل مرخص مؤكد أو اترك علامة واضحة للأصل الناقص في بيئة التطوير فقط.
- لا تضع صوراً تجميلية أو مقاطع Gameplay مصطنعة في تقرير الأدلة. كل صورة دليل يجب أن تكون ملتقطة من النسخة الفعلية، مع وصف الجهاز/المشهد والتاريخ.
- لا تستخدم موسيقى محمية دون ترخيص. إذا لم تتوفر موسيقى أصلية أو مرخصة، استخدم صمتاً أو مؤقتاً واضحاً في نسخة التطوير ولا تدّعِ وجود موسيقى نهائية.

## 29.11 بوابة الإصدار النهائي — لا تسليم مزيف

لا تعلن أن اللعبة اكتملت إلا عند تحقق جميع البنود التالية:

- المشروع يفتح بالنسخة الموثقة من Unreal Engine.
- لا توجد أخطاء Compile أو Link أو Packaging معروفة في هدف التسليم.
- ملفات الوحدات والإضافات والمراجع والخرائط والسكربتات مترابطة ولا توجد مسارات مكسورة حرجة.
- الاختبارات الحرجة تعمل ونتائجها محفوظة.
- APK arm64-v8a موجود فعلياً ويمكن التحقق من حجمه وSHA-256.
- جرى تثبيت APK وتشغيله على هاتف حقيقي، أو صُرّح بوضوح أن اختبار الجهاز `BLOCKED` وأن الملف غير مؤكد.
- وظائف الحركة والقيادة والحفظ والعمل Offline التي يدّعي التقرير وجودها تم اختبارها فعلياً.
- لا توجد أزرار وهمية أو بيانات أداء مختلقة أو أصول بلا ترخيص معلوم.
- تسليم الوثائق وسجلات الاختبارات وقائمة المشكلات المعروفة.

إذا لم تتحقق الشروط، قدّم أفضل ناتج فعلي قابل للبناء مع حالة `INCOMPLETE` أو `CANDIDATE-UNVERIFIED`، ولا تستخدم كلمة Complete/Final/Production Ready.

## 29.12 ملفات الأدلة والتسليم الإلزامية

أنشئ واملأ هذه الملفات بناءً على النتائج الفعلية، ولا تترك تقارير نجاح فارغة أو مكتوبة مسبقاً:

- `Docs/BUILD_REPORT.md`: المحرك، compiler، SDK/NDK، الأوامر الفعلية، وقت البناء، رمز الخروج، النتيجة، وروابط السجلات.
- `Docs/TEST_REPORT.md`: كل اختبار وحالته PASS/FAIL/BLOCKED/NOT RUN مع الدليل.
- `Docs/FILE_AND_DEPENDENCY_AUDIT.md`: تدقيق المسارات والملفات والوحدات والإضافات والخرائط والربط.
- `Docs/ANDROID_DEVICE_TEST_MATRIX.csv`: نتائج الأجهزة الحقيقية فقط.
- `Docs/ASSET_LICENSE_MANIFEST.csv`: مصدر ورخصة كل أصل خارجي.
- `Docs/KNOWN_ISSUES.md`: كل مشكلة مفتوحة وخطورتها وخطوة معالجتها.
- `Docs/DELIVERY_MANIFEST.txt`: أسماء الملفات التي سُلّمت وأحجامها وSHA-256.
- `Docs/WORKLOG.md`: ما تغير فعلياً في كل مرحلة وأسباب التغييرات.

يجب أن تكون أوامر البناء والاختبار في الوثائق مطابقة للأوامر التي شُغّلت فعلاً. اذكر مجلد العمل والمتغيرات المطلوبة دون كشف الأسرار. لا تكتب أمراً مفترضاً باعتباره أمراً مجرّباً.

## 29.13 صيغة التقرير الأخير للمستخدم

عند انتهاء جلسة التنفيذ، لا ترسل كلاماً تسويقياً. أرسل تقريراً عربياً واضحاً بهذا الترتيب:

1. **الحالة:** COMPLETE أو INCOMPLETE أو BLOCKED أو CANDIDATE-UNVERIFIED.
2. **ما تم تنفيذه فعلياً:** أسماء الأنظمة والملفات والمزايا التي أُنجزت.
3. **نتيجة البناء:** الأمر الفعلي، رمز الخروج، ورابط/مسار سجل البناء.
4. **نتيجة الاختبارات:** عدد PASS وFAIL وBLOCKED وNOT RUN، وأهم الأدلة.
5. **APK:** رابط/مسار الملف إن كان موجوداً فعلاً، الحجم، ABI، Version، SHA-256، وحالة تثبيته وتشغيله على جهاز حقيقي.
6. **تدقيق الربط:** نتيجة مسارات الملفات والوحدات والإضافات والخرائط والسكربتات.
7. **المشكلات المتبقية:** لا تخفِ أي خطأ أو تحذير مؤثر أو اختبار لم يُنفذ.
8. **ما يمنع الإكمال:** اذكر متطلبات محددة فقط، مثل جهاز Android غير متاح أو رخصة أصل غير مؤكدة أو أداة بناء مفقودة.

**الأمر الختامي:** لا تكتفِ بأن تقول للمستخدم ما الذي ينبغي فعله. نفّذ داخل المستودع ما تستطيع فعلياً، وابنِ واختبر وأصلح، وتحقق من الروابط والمسارات والأوامر. لا تدّعِ نجاحاً بلا دليل. إذا تعذّر إكمال أي جزء، قل ذلك صراحة وحدد سببه وأثره، ثم سلّم الملفات والسجلات الفعلية التي أنجزتها دون اختلاق.
